# code-review · 两轴代码评审

**做对了事，和把事情做好，是两个问题。** 这个 Agent Skill 用于评审已经完成的一段改动：先对照需求认定做了什么，再独立判断代码质量。两轴都给出依据，但不合并排序，也不打总分。

| 评审轴 | 核心问题 | 产出 |
| --- | --- | --- |
| **Spec**（规格） | 做的是不是要做的事？ | 逐条核对要求，并列出超出约定的改动。 |
| **Standards**（质量） | 这件事做得好不好？ | 依据仓库规范和实际后果，指出正确性缺陷及需要裁决的质量问题。 |

比如，把导出上限写成 5000 行而不是约定的 1000 行，是 **Spec 偏离**；上限实现正确，但写入中断后仍返回成功，而需求没有规定这种失败路径，是 **Standards 正确性阻断**。代码看着干净不能抵消需求偏离，需求对上了也不代表代码正确。

## 怎么用

这是一个仅含 Markdown 指令的 Skill，没有单独的 CLI、运行时或依赖需要安装。

1. **安装**：下载本仓库的 [`SKILL.md`](./SKILL.md)，保留文件名，放进你的客户端配置的 Skills 目录下的 `code-review/` 子目录。不同客户端的 Skills 目录可能不同；不支持 Skills 的客户端，可直接把文件交给 Agent 并要求按它执行。
2. **指定改动范围**：提供提交、diff，或明确的文件范围。
3. **指定评审依据**：提供需求文档、设计文档、验收条款、工单或口头约定。有多份时，注明本次采用哪一份。确实没有，也直接说明。

有明确验收条款时：

> 用 `code-review` 评审当前分支对 `main` 的 diff，以 `docs/export-spec.md` 为准。逐条核对验收要求，两轴分开输出，不修改代码。

没有书面或口头约定时：

> 用 `code-review` 评审提交 `<commit-sha>`。这次确认没有需求或设计约定，请按 Spec 降级流程执行，再独立评审代码质量，不修改代码。

## 怎么读结果

- **Spec 逐项核对表**保留原文顺序，便于回查。超出约定的改动另列；实现需求必需的测试、辅助函数等不算蔓延。没有评审依据时，只说明推断出的改动意图与实际范围，不把推断当成验收标准。
- **Standards**只审改动引入或触及的质量问题，不重复做规格判断。优先遵循仓库已有规范，跳过工具已经强制执行的规则；正确性缺陷要说明会造成什么后果，修复后需复评。
- **末尾结论**分别交代两轴状态。只有 Spec 通过且 Standards 无发现，才写「两轴均无发现」。不能核实的要求或未裁决的范围蔓延，不算 Spec 通过。

Skill **只评审，不改代码**。它可以用于交接、提交前或复评，但不会替代独立验收，也不要求另开会话；如果团队有隔离要求，可以叠加使用。

完整流程、降级规则和结论格式见 [`SKILL.md`](./SKILL.md)。
